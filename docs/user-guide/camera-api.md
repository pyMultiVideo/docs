# Camera APIs

pyMultivideo is structured to make it straightforward to add support for new camera systems.  All camera-system specific code is located in the [camera_api](https://github.com/pyMultiVideo/code/tree/main/camera_api) folder, with one Python module per supported camera system, plus a *generic_camera* module which defines the required structure of camera APIs.

Each camera API module must have the following components:

- One or more camera classes used to control and acquire video from cameras.  Camera classes must be subclassed from the `GenericCamera` class defined in the [generic_camera](https://github.com/pyMultiVideo/code/blob/main/camera_api/generic_camera.py) module.
- A `list_available_cameras` function which returns a list of serial numbers for connected cameras belonging to the camera system.
- An `initialise_camera` function which takes a camera serial number as an argument and returns a camera class instance for the specified camera.

The technical reference for these functions and classes is provided by the generic camera module itself.  The `GenericCamera` class specifies the methods and parameters that must be implemented when it is subclassed for a specific camera system, with type hints indicating the types for arguments and return values.  For examples of camera API modules for specific scientific camera systems see the [spinnaker](https://github.com/pyMultiVideo/code/blob/main/camera_api/spinnaker.py) and [ximea](https://github.com/pyMultiVideo/code/blob/main/camera_api/ximea.py) camera APIs.  The [webcam](https://github.com/pyMultiVideo/code/blob/main/camera_api/webcam.py) API shows how the camera class can be adapted to work with cameras that do not support manual control of camera parameters or return frame metadata.

Some additional notes about camera API implementation:

- Scientific camera systems typically implement a frame buffer which can temporarily store acquired frames until they are processed by the host computer.  The existence of such a frame buffer is assumed by the camera class implementation as the `get_available_images` method is designed to be called at a lower frequency than the camera sampling rate and return a list of the newly acquired images since it was last called.   The OpenCV webcam interface used by the webcam API module does not implement a frame buffer, so acquisition and buffering is handled using a separate Python thread, but this is much less performant so camera system frame buffers should be used if available.
- Images are returned as instances of a `FrameData` class, defined in the *generic_camera* module, which contain both the image data and metadata (GPIO pin state, frame timestamp, and frame number).  The frame timestamp and number should be extracted from the image metadata generated by the camera system if available, but see the webcam API for an example of generating these in Python.  Frame numbers are used to identify whether any frames have been dropped due to the camera buffer overflowing - dropped frames will be reported if frame numbers of consecutively recovered frames are not continuous. 
- If different cameras supported by the camera system require different parameters or control methods, this can be handled by having multiple camera classes defined in the camera system's API module, with the `initialise_camera` function resolving which class should be instantiated given the provided serial number.  For an example of this see the Spinnaker camera API.
